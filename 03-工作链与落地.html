工作链与落地

算法跑通一次叫「做实验」，换一个人、隔两个月、换一批机器，用同一份配置还能训出分毫不差的结果，并且顺滑推到线上不翻车，才叫「工程工作链」。

很多团队大模型后训练越做越乱，通常是因为：数据直接改在原文件夹里、超参数随手改在命令行里、评测每次换一套提示词、上线时聊天模板和训练时对不上。要把大规模迭代稳住，靠的是下面这套固定规矩。

八个制品

不管后训练算法今年流行 DPO、GRPO 还是明年的新名字，一条可复用流水线沉淀下来的永远是这八个标准制品：

制品 具体包含什么 解决什么痛点
1. 版本化数据包 内容哈希、来源明细、开源许可证、去重记录、与评测集的去污染报告、各类数据配比 防止「上次训得好，这次覆盖了数据再也找不回来」或考题漏进训练集
2. 单一配方文件 基座检查点路径、数据版本号、算法名、学习率、KL 系数、采样温度、分组大小、随机种子、聊天模板、Git Commit 把所有旋钮锁死在一份 YAML / 代码配置里，消灭口头传参
3. 统一训练启动器 SFT、DPO、GRPO 共用同一套数据加载、分布式初始化、存盘和日志外壳，只切换核心损失与采样段 避免换个算法就重写一套脚手架，减少低级工程 Bug
4. 自动实验记录 启动时自动上报配置、Git 版本、数据哈希；训练中记损失、奖励、KL、长度；结束时记检查点路径与消耗的 GPU 小时 任何没有完整登记的野生运行，一律不准进入上线候选池
5. 分层评测门禁 通用能力、历史回归集、红队安全集三张成绩单分开出；评测脚本和容器镜像同样锁死版本 防止为了刷高数学分把日常指令遵循或安全性训崩
6. 可重切分检查点 采用分布式无关格式（如 DCP），附带当前晋升状态标签（实验中 / 评测通过 / 安全通过 / 可部署） 换集群、换并行度、或者回退版本时，随时拉起就能用
7. 训推一致契约 分词器（Tokenizer）、Jinja 聊天模板、工具调用 JSON Schema、停止词（Stop Words）、系统提示词版本与权重打包在一起 根治「线下跑分挺高，一上生产接口模型就开始胡言乱语」
8. 带成本的晋升单 记录是谁、依据哪份评测与安全报告把检查点推上生产，以及这一版一共烧了多少 GPU 小时 让每次迭代有账可算，随时能按能力和安全两条线分别回滚

数据是版本化制品

千万不要在名叫 train_final_v2_new.jsonl 的文件上直接增删改。数据要像代码发版一样管理：每次改动生成一个新的不可变版本号和 SHA256 哈希。

后训练的数据仓库必须拆成三个独立抽屉：

  • 监督微调仓（SFT）：日常指令、多轮对话、工具调用轨迹、冷启动长思维链。
  • 偏好对比仓（Preference）：成对的「好回答 / 坏回答」（供 DPO / RM 用），或单条「赞 / 踩」标签（供 KTO 用）。
  • 可验证题库（Verifiable Prompts）：带标准答案的数学理化题、带单元测试用例的代码题、带格式与规则校验器的指令题（供 GRPO / DAPO 在线采样用）。

每次发版必做两道安检：MinHash / 语义向量去重（去掉复读机样本），以及评测集 N-gram 与语义去污染（把和考题长得像的训练题全部剔除）。合成数据与人工标注流水线常用 distilabel 和 Argilla。

配方是代码

严禁在 Jupyter Notebook 里临时改完学习率就直接开训。一份实验配方就是一份受 Git 管控的配置文件（Hydra 或 YAML）：

  • 输入侧锁死：基座权重哈希、数据包版本、聊天模板名称；
  • 算法侧锁死：优化器参数、学习率退火曲线、KL 惩罚系数 β、裁剪范围、采样温度、每题采样条数 G；
  • 环境侧锁死：容器镜像摘要、全局随机种子。

作业提交的瞬间，启动脚本自动把当前代码仓库的 git rev-parse HEAD 和未提交 diff 存进输出目录，保证半年后任何人拿这一份文件都能一模一样重跑出来。

实验记录绑在作业上

训练脚本一启动，不用人工干预，自动把配方、数据哈希、机器列表写进实验追踪系统；训练过程中除了看 Loss，在强化学习里尤其要盯紧四条线：平均奖励、输出平均长度（防凑字数或坍缩）、策略熵（防过早丧失探索）、相对参考模型的 KL 散度。

评测是门禁

不要把所有测试集揉成一个「平均分」——数学涨了 5 分、结果日常问答开始拒答正常请求，平均分看起来还涨了，上线就是事故。评测门禁必须拆成三张表独立一票否决：

  1. 能力表：知识、数学推理、代码生成、复杂指令遵循、长文本大海捞针、多轮工具调用。
  2. 回归表：把线上曾经出过错、或者业务最核心的几百条必考题锁成回归集，新版在这张表上不准倒退。
  3. 安全表：违规拒答率、越狱攻击防御率、以及过度拒绝率（不能把正常问题也当敏感词拒掉）。

注意评测脚本本身的提示词、Few-shot 示例、解码温度、提取答案的正则表达式，必须和训练镜像一样锁死版本。否则换一版评测脚本，历史分数就全没法比了。

奖励和验证器是独立服务

在可验证强化学习和在线偏好对齐里，打分器就是方向盘：

  • 规则与沙箱验证器：数学题要先做 LaTeX 解析和符号等价化简（比如 \frac{1}{2} 和 0.5 得判成一样）；代码题要丢进带超时和内存限制的无网容器里跑单元测试。
  • 大模型裁判（LLM-as-a-Judge）：主观写作题用强模型打分时，必须准备一份固定的人工标注校准集（Golden Set）。每次换裁判模型或改裁判提示词，先在黄金集上看一致率有没有漂移；同时要防模型靠「写得长、分点列举、套客套话」骗裁判高分。

检查点有晋升状态

训练存下来的检查点不能直接拷进线上推理目录，必须像软件发版一样走四个状态流转：

实验中 (Experimental)
  → 评测通过 (Eval-Passed)
  → 安全通过 (Safety-Passed)
  → 可部署 (Deployable)

每次状态晋升，自动把当时的评测报告链接、安全扫描结果、操作人、耗费算力写进模型卡片。线上万一发现新版本在某个垂直场景退化，可以立刻沿着记录回滚到上一个「可部署」版本；能力和安全补丁分开留档，回退业务能力时不会把刚打上的安全补丁也一起撤掉。

失败预算

大规模训练里，机器掉卡、显存偶发 ECC 错误、高优任务抢占是常态，不能把「从头到尾不中断」当成前提。

工程上靠两道保险把损失控制在几分钟以内：一是异步检查点（每几百步把状态快速落盘，不卡主训练流）；二是在强化学习里把已经采样并打完分的轨迹落盘缓存——万一训练在第 95 步崩了，重启后直接读缓存算梯度，不用把前面最烧钱的采样重跑一遍。

一次只动一个因素

新手做后训练最容易犯的错，就是「换了一批新清洗的数据 + 把 DPO 换成 GRPO + 顺手调大了学习率」，训完发现涨了 3 分，高兴地合入主干——结果根本没人知道这 3 分是谁立的功，甚至可能其中两项是正收益、一项是负收益。

严格的实验纪律只有一条：每次消融对比（Ablation）只允许改动一个变量。改数据配比就锁死算法和超参；改算法就锁死数据包和步数。只有单变量验证确认涨点的改动，才允许写进下一代基线配方。

小模型是探针

如果你要训一个 70B 或百亿 MoE 大模型，绝不能拿大图模型直接当日常试验田——洗一版数据、试一个超参就烧几千卡时，试错成本太高，迭代一慢必输。

成熟团队的做法是拿同词表的小模型（比如 1.5B / 7B）或短步数当探针（Proxy）：新清洗的数据配比、新的奖励塑形规则，先在小模型上跑通消融，确认在评测门禁上稳定涨分，再按缩放规律搬到大模型上做最终验证。同时每份实验报告必须同时报「评测得分」和「达到该分数消耗的 GPU 小时与 MFU」，算不清楚账的涨点无法规模化。

训练格式和线上格式是同一份契约

大量模型「线下评测猛如虎，线上接口像智障」，罪魁祸首都是训推不一致：

  • 训练时用的是模板 A，上线时后端工程师手拼了一套字符串模板 B；
  • 特殊分隔符（如 <|im_end|>、<think>）或停止词没对齐，导致模型停不下来或者提前截断；
  • 工具调用（Function Calling）的参数说明格式和训练时不一样。

规矩很简单：分词器配置、tokenizer_config.json 里的 Jinja 聊天模板、工具 JSON Schema、默认系统提示词、停止词列表，必须和模型权重绑在同一个制品目录里一起交付，线上推理服务直接加载同一份模板渲染输入，禁止业务后端自己手拼提示词字符串。

上线前通常还要过一道量化与加速关：把 BF16 权重压成 FP8 或 INT4（AWQ / GPTQ），或者配一个极小的草稿模型做投机解码（EAGLE，一次猜好几个词再由主模型并行验证，丝毫不损生成质量但大幅提速）。量化后的模型必须重新跑一遍评测门禁，确认没把数学和代码能力压坏，再看线上三大硬指标：首字延迟（TTFT）、每词生成间隔（TPOT）、单卡并发吞吐。

线上反馈回到训练集

模型上线不是结束，而是下一轮数据的起点：

  1. 收集线上真实失败案例（用户追问纠正、点踩、工具调用报错、长尾难题）；
  2. 先过严格的隐私脱敏（去掉姓名、电话、密钥、内部代码）和垃圾过滤；
  3. 把典型错题送进标注或验证器流水线，生成新的 SFT 示范、偏好对或可验证题；
  4. 和评测集做去污染，并严格控制回灌数据在新一版训练集里的占比上限（防止模型反复吃自己生成的语料导致分布退化），打包成下一个数据版本号，进入下一轮迭代。

和基础设施怎么接上

把三篇笔记合在一起，整条工业级后训练流水线就是这样一个闭环：

版本化数据包 + 单一配方文件
  → 统一启动器提交到 Slurm / Kueue 集群
  → 3D 并行训练 + vLLM / SGLang 采样 + 独立验证器打分
  → 异步可重切分检查点 + 自动上报实验看板与 GPU 小时
  → 能力 / 回归 / 安全三道评测门禁
  → 量化 / 蒸馏 / 投机解码 + 训推一致契约上线
  → 线上真实交互脱敏清洗 → 生成下一代数据包

基础设施保住的是「算得快、不掉链子」，工作链保住的是「每一次涨点都能攒下来、接得上」。两手都硬，团队才算真正拥有了持续迭代基模和行业模型的能力。
